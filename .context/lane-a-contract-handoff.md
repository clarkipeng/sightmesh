## Proposed contract shape (design reasoned through, not yet implemented)

1. **New file `crates/executors/src/outcome.rs`** (register via `pub mod outcome;` in `crates/executors/src/lib.rs`):
   - `ExecutionOutcomeClass` enum, exactly the 9 plan §9 variants (`quota_exhausted | auth_expired | auth_invalid | model_unavailable | rate_limited_transient | network_transient | user_stopped | task_failed | unknown`), `sqlx::Type` + `Serialize`/`Deserialize` (snake_case) + `TS`, mirroring `ExecutionProcessStatus`'s derive shape but stored as `TEXT` (SQLite has no named enum types).
   - `BindingScope` enum (`account | route | global`) for the plan §14 `binding_scope` field.
   - `NormalizedOutcome` struct matching the plan §14 JSON contract exactly: `class`, `provider_code: Option<String>`, `retry_after_seconds: Option<i64>`, `resets_at: Option<DateTime<Utc>>`, `binding_scope: Option<BindingScope>`, `safe_message: Option<String>`, with a small builder (`::new(class).with_provider_code(..).with_safe_message(..).with_binding_scope(..)`).
   - Pure, unit-testable classifier functions, each citing its exact source signal in a doc comment:
     - `classify_codex_executor_error(&ExecutorError) -> NormalizedOutcome` — `AuthRequired` → `AuthExpired` (binding_scope `Account`, provider_code `"codex_account_requires_openai_auth"`), citing `codex.rs:594-600`'s `requires_openai_auth && account.is_none()` check. Rationale for `AuthExpired` over `AuthInvalid`: no secret was ever resolved to be *wrong* — the account is simply not logged in, and `AuthExpired`'s corrective action ("notify reauthentication, select next owned binding") is the right one; `AuthInvalid`'s "never retry same secret automatically" doesn't apply since there's no secret to blame. All other `ExecutorError` variants → `Unknown` (no provider code behind them — do not guess).
     - `classify_claude_result(subtype: Option<&str>, is_error: Option<bool>, error: Option<&str>) -> Option<NormalizedOutcome>` — `None` when not an error; otherwise `Unknown` class (no confirmed error-subtype taxonomy exists in this repo) but with `subtype` preserved verbatim as `provider_code` for forward audit, and `error` preserved as `safe_message`. Fails closed per plan invariant 10 rather than guessing what e.g. `error_max_turns` would mean.
     - `classify_claude_rate_limit_event() -> NormalizedOutcome` — `RateLimitedTransient`, `provider_code: "claude_rate_limit_event"`, generic `safe_message`. Deliberately does **not** attempt to parse `rate_limit_info`'s fields (no confirmed schema — see file map above).
   - A full first-draft of this file (unbuilt, untested in situ) exists only in `stash@{0}` — read for a starting point, but re-verify every claim against the file map above before trusting it, and re-run `cargo check -p executors` / `cargo test -p executors outcome::` before relying on it.

2. **`ExecutionProcess` DB extension** (new migration `crates/db/migrations/20260818120000_add_execution_outcome_to_execution_processes.sql` or later timestamp — check for newer teammate migrations before picking a timestamp):
   - `ALTER TABLE execution_processes ADD COLUMN` for `outcome_class TEXT CHECK (... IN (9 values) ...)`, `provider_code TEXT`, `retry_after_seconds INTEGER`, `resets_at TEXT`, `binding_scope TEXT CHECK (... IN ('account','route','global'))`, `safe_message TEXT` — all nullable, flat columns (matches this table's existing flat-column convention rather than a nested JSON blob).
   - Mirror into the `ExecutionProcess` Rust struct as `Option<ExecutionOutcomeClass>` / etc., plus a `normalized_outcome(&self) -> Option<NormalizedOutcome>` accessor.
   - Requires editing all 8 `query_as!` call sites (see file map) to add the 6 columns with nullable casts (`ep.outcome_class as "outcome_class?: ExecutionOutcomeClass"`, same pattern as the existing `completed_at?: DateTime<Utc>`).
   - New `update_completion_with_outcome(pool, id, status, exit_code, outcome: Option<NormalizedOutcome>)`; keep the existing `update_completion(pool, id, status, exit_code)` signature as a thin wrapper (don't break its ~10 call sites) that passes `None` **except** it should auto-derive `Some(NormalizedOutcome::new(UserStopped))` when `status == Killed` — that's cdesktop's own signal (an explicit stop), not a guessed provider signal, so it's safe to default.
   - Explicit scope call made here: do **not** thread a classified outcome through `local-deployment`'s generic exit monitor in this pass (see Exclusions) — expose the classifiers and the DB contract so Lane B/D can call them from their own exit-handling integration.

3. **`SessionCommand` DB extension** (separate migration, e.g. `20260818120100_add_attempt_metadata_to_session_commands.sql`) — assignment explicitly directs these fields onto `SessionCommand` (the stable "logical command"), not onto `ExecutionProcess`, because `SessionCommand.execution_process_id` already tracks "the current claimant attempt," so `attempt`/`route_id`/etc. describe *that* current attempt and get overwritten on each requeue:
   - New nullable/defaulted columns: `attempt INTEGER NOT NULL DEFAULT 1`, `route_id TEXT`, `auth_binding_id TEXT`, `account_alias TEXT`, `executor TEXT`, `model TEXT`, `billing_class TEXT` (deliberately unconstrained — it's Lane C's settings vocabulary, not yet stabilized, so no `CHECK` here), `policy_digest TEXT`, `predecessor_execution_process_id BLOB REFERENCES execution_processes(id) ON DELETE SET NULL`.
   - `auth_binding_id` must be excluded from the struct's default `Serialize`/`TS` output (public API projections must omit it per plan §14's last paragraph) — plan `#[serde(skip_serializing)]` (codebase precedent: `#[ts(skip)]` is used elsewhere, e.g. `crates/executors/src/executors/codex.rs:185`, `crates/executors/src/logs/mod.rs:119`) while still being a normal readable/writable Rust field for internal (non-serde) code paths that need the opaque id.
   - A requeue-with-attempt-increment method (e.g. `requeue_execution_for_retry` or extending `requeue_execution` itself) that atomically bumps `attempt` and records the outgoing `execution_process_id` as the new `predecessor_execution_process_id` on the next claim — needs careful design so it stays a single scoped `UPDATE ... WHERE execution_process_id = ?`, matching the existing exact-once pattern; don't introduce a read-then-write race.

4. **`auth_binding_id` on `ExecutionEnv`** (`crates/executors/src/env.rs`): add `pub auth_binding_id: Option<String>` next to `provider_codex`, threaded from `SessionCommand.config`/`SessionCommandConfig` at launch time. Purely an opaque pass-through — do not touch `Provider::resolved_api_key()` (`crates/db/src/models/provider.rs:539-546`) beyond this. Note explicitly in the eventual PR body: **no secret-redaction utility exists anywhere in `crates/executors`, `crates/db`, `crates/services`, or `crates/server` today** — flag as a known gap for Lane B, do not attempt to build one here.

5. **Exact-once / stale-attempt guard**: analysis so far shows the existing `claim_pending`/`ensure_claimed`/`release_execution`/`requeue_execution`/`finish_execution` methods are *already* exact-once-safe by construction, because every mutating query is scoped by an exact `WHERE execution_process_id = ?` match — once a command's `execution_process_id` column moves to a new attempt (via `claim_pending`), a stale predecessor's calls naturally match zero rows. The concrete gap to add, not yet built: a `SessionCommand::is_stale_attempt(pool, execution_process_id) -> Result<bool, sqlx::Error>` helper (`SELECT NOT EXISTS(SELECT 1 FROM session_commands WHERE execution_process_id = ? AND state = 'claimed')`) that callers (the future Lane D reconciler, and `cleanup_orphan_executions`) must consult before treating an attempt's outcome as authoritative for relaunch — wire it defensively into `cleanup_orphan_executions` (`container.rs:333-387`) even though today it's provably a no-op given the 1:1 process:command mapping, specifically so the invariant is *named, tested, and load-bearing* once `predecessor_execution_process_id` chains make multi-attempt races real.
